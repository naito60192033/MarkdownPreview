# 教訓(ユーザー指摘から得たパターン)

## L1: 表示文言のテストは「期待する文言が出ていること」を確かめる(確認日 2026-09-14・確定)
- 事象: 名前の変更の完了メッセージ(move / コピー方式の見分けに使う)の E2E が
  `!msg.includes('コピー方式')` だけを確かめており、メッセージが空でも、後続の操作(保存)の
  「保存しました」に置き換わっていても通っていた
- 対策: 文言の検査は `assert.equal(msg, '期待文言')` か `waitFor(() => msg === '期待文言')` で、
  **その操作の直後に**(後続の操作でステータスが上書きされる前に)行う。「〜が出ていない」だけの検査は
  空文字で素通りする
- 実機の確認に使う文言(方式の見分けなど)は自動で消さない(ユーザーが見る前に消えると確認できない)

## L2: 実機での確認を頼むときは「どこに・何が出るか」を具体的に書く(確認日 2026-09-14・確定)
- 事象: 「完了時の表示を見てください」とだけ頼んだため、完了メッセージ(ステータスバー右下の小さな文字)に
  気付かれず「メッセージが表示されない」と報告された(実際には出ていた)
- 対策: 画面上の場所(例:「画面最下部のステータスバーの右端」)と、出る文言そのものを書く。
  ステータスバーの文言は目立たないので、トーストやダイアログを想像されやすい

## L3: 実機で試してもらうビルドは、いつもの `MarkdownPreview\dist\mdpreview.html` に置く(確認日 2026-09-15・確定)
- 事象: 別セッションと並行するため git worktree(`../MarkdownPreview-paste`)で実装し、その dist を開くよう
  頼んだが、ユーザーはいつもの `MarkdownPreview\dist\mdpreview.html`(dev のビルド)を開き、
  「保存中の表示もメニューも出ない」と報告された
- 対策: 実機確認を頼む前に、いつもの作業ツリーをそのブランチに切り替えてビルドし、そのファイルに
  新しい機能が入っていることを確かめてから頼む(worktree は開発中だけ使い、確認の前に片付ける)。
  別の場所を開いてもらうしかないときは、パスの違いを冒頭で強調する
- 確かめ方: dist の中の新しいクラス名などを grep する(esbuild は日本語を \u エスケープするので、日本語の文言では grep できない)

## L4: 見た目を左右する決め事は「参考に合わせる」で決め打ちせず、確認の問いで選んでもらう(確認日 2026-09-15・確定)
- 事象: サイドバー目次を「Qiita と同じ右側」と計画ファイルに書いただけで実装し、実装後に「左側にしたい」と言われた
  (計画は承認されていたが、配置は会話の中で選択肢として示していなかった)
- 対策: 配置(左右・上下)・既定のオン/オフ・出す/出さない画面幅など、実物を見て初めて気付かれやすい見た目の決め事は、
  計画ファイルに書くだけでなく、確認の問い(AskUserQuestion 等)で明示的に選んでもらう。参考にするサイトがあっても同じ
